# express-cursors-app

Навчальний сервер на **Node.js + Express.js** з даними у **MongoDB Atlas** (Mongoose), авторизацією через **Passport**
та шаблонізаторами **PUG / EJS**. Проєкт побудований за патерном **MVC**.

## Що нового (HW 67.1)

| Тема                    | Що додано                                                                                          |
| ----------------------- | -------------------------------------------------------------------------------------------------- |
| **Курсори**             | Потокове вивантаження статей (`/api/articles/export`) і підрахунок статистики обходом курсора (`/api/stats/scan`) — без збереження всіх документів у масиві |
| **Агрегаційні запити**  | Чотири конвеєри `aggregate()` для статистики: `overview`, `authors`, `tags`, `timeline`            |
| **Робота з великими даними** | Генератор 50–100 тисяч статей, скрипт `benchmark`, вимірювання пам'яті сервера в `/health`    |

Попередній функціонал (CRUD-операції `insertOne … deleteMany`, `find` з проєкцією) описано в
[`HW66-crud-api.md`](HW66-crud-api.md) і працює без змін.

Потрібен Node.js 18+.

```bash
npm install
```

Створіть файл **`.env`** (за зразком `.env.example`; він у `.gitignore`):

```env
MONGODB_URI=mongodb+srv://myUser:myPassword@cluster0.xxxxx.mongodb.net/express_app?retryWrites=true&w=majority
```

Як отримати `MONGODB_URI` в Atlas: *Database Access* → користувач із правом читання/запису; *Network Access* → додайте свою IP-адресу;

(спецсимволи в паролі кодуються: `@` → `%40`). Повна інструкція — в `HW66-crud-api.md`.

```bash
npm start
```

Перевірка: <http://localhost:3000/health> → `OK`, стан бази й **пам'ять сервера** (знадобиться для порівнянь нижче).
Вхід: `admin@example.com` / `admin123` (або `user@example.com` / `user123`).

> У PowerShell використовуйте **`curl.exe`** (не `curl`) і екрануйте лапки в JSON як `\"`. Якщо `npm` заблоковано політикою виконання:

# 1. Курсори

## Що таке курсор і навіщо він потрібен

Звичайний запит `await Article.find()` повертає **масив усіх документів**: поки вони не завантажені всі, нічого не відбувається,
а в пам'яті сервера одночасно лежить уся вибірка (а потім ще й її текстове представлення). Чим більше колекція — тим більше пам'яті,
аж до `JavaScript heap out of memory`.

**Курсор** — це «вказівник» на результат запиту на стороні MongoDB. База віддає документи **порціями** (`batchSize`),
а код бере їх по одному:

```js
const cursor = Article.find(filter).lean().cursor({ batchSize: 1000 });
for await (const doc of cursor) {
  // обробили один документ — він одразу може бути забутий збирачем сміття
}
```

У пам'яті одночасно лише одна порція, тому **використання пам'яті не залежить від розміру колекції**.

### Використані методи Mongoose

| Метод                                | Призначення                                                                         |
| ------------------------------------ | ----------------------------------------------------------------------------------- |
| `Query.cursor({ batchSize })`        | Створює курсор (`QueryCursor`) замість завантаження масиву                          |
| `cursor.next()`                      | Бере наступний документ (`null`, коли документи закінчились)                        |
| `for await (const doc of cursor)`    | Асинхронна ітерація по курсору                                                      |
| `cursor.eachAsync(fn)`               | Викликає `fn` для кожного документа й чекає її завершення (зворотний тиск)         |
| `cursor.close()`                     | Закриває курсор на сервері MongoDB                                                  |
| `.lean()`                            | Повертає прості об'єкти без «обгортки» Mongoose — швидше й економніше за пам'яттю   |

## 1.1. `GET /api/articles/export` — потокове вивантаження

**Реалізація:** `controllers/articlesExportController.js` → `exportArticles`. Серіалізатори форматів — `utils/exporters.js`.

Як це працює:
1. `parseExportQuery` перевіряє параметри (при помилці — `400` JSON, потік ще не почався).
2. Створюється курсор: `Article.find(filter, projection).sort({ _id: 1 }).lean().cursor({ batchSize })`. Сортування за `_id` гарантує, що документи не повторюються й не губляться.
3. **Перший документ береться до відправки заголовків** — якщо база недоступна, клієнт отримає нормальну помилку, а не обірваний потік.
4. Асинхронний генератор `chunks()` віддає «шматки» відповіді (`yield`): заголовок, кожен документ, завершення.
5. `stream.pipeline(Readable.from(chunks()), res)` пише шматки у відповідь і **стежить за зворотним тиском (backpressure)**: якщо клієнт читає повільно, генератор призупиняється, і ми не витягуємо з бази більше, ніж можемо відправити.
6. У блоці `finally` генератора курсор **завжди закривається** — і після успіху, і коли клієнт обірвав з'єднання.

### Параметри

| Параметр      | Значення                    | Опис                                                                                   |
| ------------- | --------------------------- | -------------------------------------------------------------------------------------- |
| `format`      | `ndjson` (за замовч.), `json`, `csv` | Формат відповіді                                                              |
| `mode`        | `cursor` (за замовч.), `array` | `array` — **наївний** спосіб «усе в масив», **лише для порівняння**                |
| `batchSize`   | 1–10 000 (за замовч. 1000)  | Скільки документів курсор отримує від бази за один обмін                               |
| `limit`       | 1–10 000 000                | Обмежити кількість документів                                                          |
| `fields` / `exclude` | напр. `title,tags`   | Проєкція: які поля віддавати (як у `GET /api/articles`)                                |
| `q`, `tag`, `author`, `from`, `to` | —              | Фільтри (як у `GET /api/articles`)                                                     |

### Формати

| Формат   | `Content-Type`                        | Особливості                                                                              |
| -------- | ------------------------------------- | ---------------------------------------------------------------------------------------- |
| `ndjson` | `application/x-ndjson`                | Один JSON-документ на рядок. Найзручніший для потоків: кожен рядок можна розбирати окремо |
| `json`   | `application/json`                    | Валідний JSON-масив, який дописується поступово (`[`, документи через кому, `]`)          |
| `csv`    | `text/csv`, `attachment`              | Для Excel: BOM для кирилиці, екранування `,` `"` і переносів, захист від CSV-ін'єкції (комірки, що починаються з `= + - @`, отримують префікс `'`); масиви тегів з'єднуються через `;` |

```
Transfer-Encoding: chunked                    Content-Length: 102021485   (усе тіло відоме заздалегідь)
X-Export-Mode: cursor
```

```json
{ "error": "format: дозволені значення ndjson, json, csv" }
{ "error": "Параметри fields і exclude не можна використовувати разом" }
{ "error": "batchSize: ціле число від 1 до 10000" }
{ "error": "Параметр tag має бути рядком" }
```

### Обмеження

- Незайнятий курсор MongoDB закриває через ~10 хвилин простою — експорт, що триває довше й дуже повільно читається клієнтом, може обірватися.
- Курсор не є «знімком» колекції: документи, додані під час експорту, можуть як потрапити в нього, так і ні (сортування за `_id` гарантує лише відсутність дублів).
- Якщо помилка трапиться **після** відправки заголовків, змінити статус уже неможливо — з'єднання закривається, помилка потрапляє в журнал сервера.

# 2. Агрегаційні запити

**Агрегація** (`aggregate()`) — це конвеєр стадій (`pipeline`), що виконується **всередині MongoDB**: кожна стадія отримує результат попередньої. До Node.js приходить лише
готова відповідь (кілька десятків байтів), а не мільйони документів.

Загальні принципи, застосовані в проєкті:

| Прийом                          | Навіщо                                                                                              |
| ------------------------------- | --------------------------------------------------------------------------------------------------- |
| `$match` — **перша** стадія     | Відсіює документи до групування й дозволяє MongoDB скористатися індексом (`createdAt`, `author`, `tags`) |
| `$limit` **перед** `$lookup`    | З колекції `users` шукаємо лише топ-N авторів, а не всіх                                            |
| `allowDiskUse: true`            | Якщо проміжні дані не вміщаються в пам'ять, MongoDB скидає їх на диск                                |
| `maxTimeMS: 60000`              | Запит, що виконується довше хвилини, MongoDB перериває сам                                          |
| Фільтри з білого списку         | Клієнт передає лише `q`, `tag`, `author`, `from`, `to` — сирий `$match` від клієнта неприйнятний (захист від NoSQL-ін'єкцій) |
| `author` → `ObjectId`           | У `find()` Mongoose сам перетворює рядок на ObjectId, а в `aggregate()` — **ні**; без цього фільтр за автором нічого б не знайшов |

Усі маршрути приймають спільні фільтри та `explain`:

| Параметр                          | Опис                                                                                      |
| --------------------------------- | ----------------------------------------------------------------------------------------- |
| `q`, `tag`, `author`, `from`, `to` | Фільтри, що стають першою стадією `$match`                                               |
| `explain=true`                    | Замість даних повертає план виконання (`executionStats`) — формат залежить від версії сервера |

У кожній відповіді є поле `pipeline` — **який саме конвеєр було виконано**, і `durationMs` — час виконання.

## 2.1. `GET /api/stats/overview` — загальна статистика

Конвеєр (`overviewPipeline`): `$match` → `$facet` із трьома підконвеєрами, що працюють над одним набором документів за один прохід:

```js
[
  { $match: filter },                       // лише якщо передано фільтри
  { $facet: {
      totals: [{ $group: {                  // підсумки по всій вибірці
        _id: null,
        articles:        { $sum: 1 },
        totalCharacters: { $sum:  { $strLenCP: '$content' } },
        avgLength:       { $avg:  { $strLenCP: '$content' } },
        minLength:       { $min:  { $strLenCP: '$content' } },
        maxLength:       { $max:  { $strLenCP: '$content' } },
        tagUses:         { $sum:  { $size: { $ifNull: ['$tags', []] } } },
        withoutTags:     { $sum:  { $cond: [{ $eq: [{ $size: { $ifNull: ['$tags', []] } }, 0] }, 1, 0] } },
        firstArticleAt:  { $min: '$createdAt' },
        lastArticleAt:   { $max: '$createdAt' },
      } }],
      authors: [{ $group: { _id: '$author' } }, { $count: 'n' }],                          // унікальні автори
      tags:    [{ $unwind: '$tags' }, { $group: { _id: '$tags' } }, { $count: 'n' }],      // унікальні теги
  } },
]
```

Використані оператори: `$sum`, `$avg`, `$min`, `$max` (акумулятори), `$strLenCP`, `$size`, `$cond`, `$ifNull` (вирази), `$unwind`, `$count`, `$facet`.
Кількість **унікальних значень** рахується як «згрупувати за полем → порахувати групи» — це не вимагає тримати всі значення в одному документі.

```bash
curl.exe -b cookies.txt -G http://localhost:3000/api/stats/overview -d "to=2026-10-01"
```

```json
{
  "operation": "aggregate",
  "description": "$match -> $facet( $group | $group + $count | $unwind + $group + $count )",
  "durationMs": 1677,
  "pipeline": [ "..." ],
  "data": {
    "articles": 50000,
    "uniqueAuthors": 8,
    "uniqueTags": 24,
    "totalCharacters": 47126791,
    "avgLength": 942.54,
    "minLength": 213,
    "maxLength": 1745,
    "tagUses": 124526,
    "withoutTags": 8432,
    "firstArticleAt": "2025-08-27T00:16:35.544Z",
    "lastArticleAt": "2026-09-30T23:57:23.814Z"
  }
}
```

**Перевірка коректності:** об'єкт `data` збігається з відповіддю `/api/stats/scan` до останнього знака (і `npm run benchmark` це перевіряє).
Порожня вибірка (напр. `from=2099-01-01`) дає нулі та `null` для мін/макс/дат.

## 2.2. `GET /api/stats/authors` — рейтинг авторів

Параметр: `limit` (1–100, за замовч. 10). Конвеєр (`authorsPipeline`):

```js
[
  { $match: filter },
  { $group: { _id: '$author', articles: { $sum: 1 }, avgLength: { $avg: LEN }, tagUses: { $sum: TAGS },
              firstArticleAt: { $min: '$createdAt' }, lastArticleAt: { $max: '$createdAt' } } },
  { $sort:  { articles: -1, _id: 1 } },    // _id — для стабільного порядку при рівній кількості
  { $limit: limit },                       // спершу відсікаємо топ-N ...
  { $lookup: { from: 'users', localField: '_id', foreignField: '_id',     // ... і лише для них шукаємо імена
               pipeline: [{ $project: { username: 1 } }], as: 'user' } },
  { $project: { _id: 0, authorId: '$_id', username: { $ifNull: [{ $arrayElemAt: ['$user.username', 0] }, null] },
                articles: 1, avgLength: { $round: ['$avgLength', 1] }, tagUses: 1, firstArticleAt: 1, lastArticleAt: 1 } },
]
```

(Тут і далі `LEN` — скорочення для `{ $strLenCP: { $ifNull: ['$content', ''] } }`, а `TAGS` — для `{ $size: { $ifNull: ['$tags', []] } }`; у коді вони названі `TEXT_LENGTH` і `TAG_COUNT`.)

`$lookup` — аналог SQL `JOIN`: підтягує документ автора з колекції `users` (у підконвеєрі беремо лише `username`, тож хеші паролів ніколи не покидають базу).
Якщо автора видалили, `username` буде `null`.

## 2.3. `GET /api/stats/tags` — найпопулярніші теги

Параметр: `limit` (1–100, за замовч. 10). Конвеєр (`tagsPipeline`):

```js
[
  { $match: filter },
  { $unwind: '$tags' },                                               // стаття з 3 тегами -> 3 документи
  { $group: { _id: '$tags', articles: { $sum: 1 }, authors: { $addToSet: '$author' } } },   // $addToSet — лише унікальні автори
  { $project: { _id: 0, tag: '$_id', articles: 1, uniqueAuthors: { $size: '$authors' } } },
  { $sort: { articles: -1, tag: 1 } },
  { $limit: limit },
]
```

`$unwind` розгортає масив у окремі документи, тому статті без тегів у результат не потрапляють.

## 2.4. `GET /api/stats/timeline` — динаміка публікацій

Параметри: `interval` = `day` (за замовч.) | `month` | `year`, `limit` (1–366, за замовч. 30 — останні N періодів). Конвеєр (`timelinePipeline`):


# 3. Як оптимізації покращують роботу з великими даними

## Генерація великої колекції

```bash
npm run seed:large            # 50 000 статей (≈ 100 МБ даних, ~15–20 с)
npm run seed:large -- 100000  # 100 000 статей
npm run seed:clear            # видалити все згенероване
```

Скрипт `scripts/seed-large.js` створює 8 службових авторів (`author1@bulk-seed.local` …) і вставляє статті пачками по 2000 нативним драйвером (`insertMany` без створення документів Mongoose — найшвидший спосіб масового завантаження).
Дані **детерміновані** (фіксований генератор випадкових чисел): однаковий запуск дає однакові тексти, теги й дати, тому статистику в цьому README можна відтворити.
Повторний запуск **додає** статті до наявних — для чистого результату спершу виконайте `npm run seed:clear`.

> Безкоштовний кластер Atlas **M0 обмежений 512 МБ**. 50 000 статей вміщаються з запасом; для 100 000 стежте за розміром у вкладці *Metrics*.

| **Масив: пам'ять росте разом з даними** (локально 470 → 848 МБ при ×2 даних) | У пам'яті одночасно всі документи **і** їхній JSON-рядок                                      |

Практичний висновок: масив «усе в пам'яті» росте разом з колекцією (на 100 000 статей локально — майже 1 ГБ) і при подальшому зростанні даних впаде з `heap out of memory`,
тоді як курсор споживає стільки ж, скільки на меншій колекції. А для **підрахунку** статистики найкращий варіант — агрегація, а не обхід документів у Node.js.

> **Про вимірювання.** Блок «Atlas» отримано на хмарному кластері Atlas, блоки «Локальний сервер» — на локальному MongoDB-сумісному сервері (FerretDB 2 + PostgreSQL), де мережевої затримки практично немає.
> Тому **час** на Atlas відрізняється (видно на прикладі агрегації та загального часу експорту), а **пам'ять** «масив / курсор» визначається поведінкою процесу Node.js і за тенденцією збігається.
> Щоб побачити зростання на вашому кластері: виконайте `npm run seed:large` ще раз (стане 100 000 статей) і повторіть `npm run benchmark` — пам'ять масиву зросте, курсора — ні.
> Абсолютні числа залежать від кластера, мережі та комп'ютера, тож робіть вимірювання на своєму оточенні.

## Вимірювання на живому сервері (HTTP, локальний сервер)

Ті самі висновки можна перевірити на запущеному сервері. Рядок `Пам'ять сервера` у відповіді `/health` показує `rss`, `heapUsed` і **пік RSS** (він лише зростає, тому між вимірами **перезапускайте сервер**).

| Режим     | Перший байт | Усього  | Пік RSS сервера | Пік до експорту → після |
| --------- | ----------- | ------- | --------------- | ----------------------- |

# 4. Інструкція з тестування

Усі приклади — для PowerShell (`curl.exe`). У bash/Git Bash замість `curl.exe` пишіть `curl`, а замість `-o NUL` — `-o /dev/null`.

## Крок 0. Підготовка

```bash
npm install
npm run seed:clear            # на випадок попередніх запусків
npm start                     # у першому терміналі; запам'ятайте, що сервер створив 2 стартові статті
npm run seed:large            # у другому терміналі: 50 000 статей
curl.exe -c cookies.txt -X POST http://localhost:3000/login -H "Content-Type: application/json" -d "{\"email\":\"admin@example.com\",\"password\":\"admin123\"}"
```

Очікується: `Готово за ... с. Усього статей у колекції: 50002` і відповідь `Вхід виконано: admin@example.com`.

## Крок 1. Агрегація та курсор дають однаковий результат

```bash
curl.exe -b cookies.txt "http://localhost:3000/api/stats/overview?to=2026-10-01"
curl.exe -b cookies.txt "http://localhost:3000/api/stats/scan?to=2026-10-01"
```

**Очікується:** в обох відповідях `data` однакова (`articles: 50000`, `uniqueAuthors: 8`, `uniqueTags: 24`, `avgLength: 942.54`, …, див. розділи 1.2 і 2.1),
а `documentsTransferred` у `/scan` дорівнює 50000. Порівняйте `durationMs`: агрегація, як правило, швидша.

## Крок 2. Фільтри працюють однаково в усіх маршрутах

```bash
curl.exe -b cookies.txt "http://localhost:3000/api/articles?tag=express&to=2026-10-01&limit=1"      # поле total
curl.exe -b cookies.txt "http://localhost:3000/api/stats/overview?tag=express&to=2026-10-01"        # data.articles
curl.exe -b cookies.txt "http://localhost:3000/api/articles/export?tag=express&to=2026-10-01" | Measure-Object -Line
```

**Очікується:** те саме число (кількість статей з тегом `express`) у `total`, `data.articles` і кількості рядків експорту.

## Крок 3. Експорт: кількість і формати

```bash
curl.exe -b cookies.txt "http://localhost:3000/api/articles/export" | Measure-Object -Line          # очікується 50002
curl.exe -b cookies.txt "http://localhost:3000/api/articles/export?format=csv" -o articles.csv       # відкрийте в Excel
curl.exe -b cookies.txt "http://localhost:3000/api/articles/export?format=json&limit=3"              # валідний JSON-масив з 3 елементів
```

**Очікується:** 50002 рядки ndjson; `articles.csv` відкривається в Excel з коректною кирилицею; у третьому запиті — `[`, три документи через кому, `]`.
Режим `mode=array` дає **той самий вміст** (можна порівняти файли).

## Крок 4. Потік справді іде частинами

```bash
curl.exe -i -b cookies.txt "http://localhost:3000/api/articles/export?limit=1"
```

**Очікується:** у заголовках `Transfer-Encoding: chunked`, `X-Export-Mode: cursor` і **немає** `Content-Length`. Для `mode=array` — навпаки, є `Content-Length`.

## Крок 5. Різниця у часі першого байта

```bash
curl.exe -s -b cookies.txt -o NUL -w "перший байт: %{time_starttransfer}s, усього: %{time_total}s\n" "http://localhost:3000/api/articles/export?mode=cursor"
curl.exe -s -b cookies.txt -o NUL -w "перший байт: %{time_starttransfer}s, усього: %{time_total}s\n" "http://localhost:3000/api/articles/export?mode=array"
```

**Очікується:** у `cursor` перший байт приходить майже одразу (частки секунди), у `array` — лише наприкінці (кілька секунд на 50 000 статей).

## Крок 6. Різниця в пам'яті сервера

1. Перезапустіть сервер. Відкрийте <http://localhost:3000/health> — запам'ятайте `пік rss`.
2. Виконайте `.../export?mode=cursor` (як у кроці 5). Знову відкрийте `/health` — пік зріс на **десятки** МБ.
3. Перезапустіть сервер і повторіть для `mode=array` — пік зросте на **сотні** МБ (у нашому вимірюванні 100 → 609 МБ проти 101 → 155 МБ).

## Крок 7. Автоматичне порівняння

```bash
npm run benchmark
```

**Очікується:** таблиці, як у розділі 3, і рядок `Результати агрегації й курсора ЗБІГАЮТЬСЯ ✔`. Число «у N раз(ів) менше пам'яті» залежить від вашого комп'ютера, але курсор завжди помітно економніший.
Щоб побачити зростання, виконайте `npm run seed:large` ще раз (стане 100 000) і повторіть `npm run benchmark`: пам'ять масиву зросте, курсора — ні.

## Крок 8. Обрив завантаження

```bash
curl.exe -b cookies.txt --limit-rate 50k --max-time 1 -o NUL -w "отримано %{size_download} байт\n" "http://localhost:3000/api/articles/export"
curl.exe -b cookies.txt "http://localhost:3000/api/articles/export?limit=5" | Measure-Object -Line
```

**Очікується:** за секунду повільний клієнт отримує лише ~100 КБ із ~100 МБ (зворотний тиск: сервер не «забігає вперед»), сервер продовжує працювати, наступний запит повертає 5 рядків, а в консолі сервера немає помилок (курсор закрито).

## Крок 9. Помилки

```bash
curl.exe -b cookies.txt "http://localhost:3000/api/articles/export?format=xml"            # 400 + JSON
curl.exe -b cookies.txt "http://localhost:3000/api/stats/tags?limit=0"                    # 400 + JSON
curl.exe "http://localhost:3000/api/stats/overview"                                       # 401 + JSON (без cookie)
curl.exe -g -b cookies.txt 'http://localhost:3000/api/stats/overview?author[$ne]=x'      # 400: параметр має бути рядком (одинарні лапки й -g: PowerShell не розкриє $ne, а curl — []);
```

## Перегляд виконаних операцій

Запустіть сервер із `MONGOOSE_DEBUG=true` (PowerShell: `$env:MONGOOSE_DEBUG="true"; npm start`) — у консолі видно, що саме йде в базу: `articles.find(...)` з проєкцією для курсорів, `articles.aggregate([...])` для статистики.
Не вмикайте цей режим у production: у вивід можуть потрапити хеші паролів.

## Типові проблеми

| Симптом                                                  | Причина і рішення                                                                                      |
| -------------------------------------------------------- | ------------------------------------------------------------------------------------------------------ |
| `Не задано MONGODB_URI` / `bad auth` / `ETIMEDOUT`       | Перевірте `.env`, пароль користувача бази та Network Access в Atlas                                    |
| `querySrv ... <cluster>.mongodb.net`                     | У `.env` залишився шаблон із `<cluster>` — вставте свою реальну строку підключення                      |
| `401` на `/api/...`                                      | Не виконано вхід або не передано cookie (`-b cookies.txt`)                                             |
| Числа статистики відрізняються від README                | У базі є інші дані: виконайте `npm run seed:clear`, потім `npm run seed:large`, додайте `to=2026-10-01` |
| Статистика через `author=...` повертає нулі              | `author` має бути `_id` автора (24 hex-символи), а не його ім'я — візьміть його з `/api/stats/authors` |
| `benchmark` показує мало різниці                         | Замало даних — створіть більше: `npm run seed:large -- 100000`                                         |
| Atlas M0: `you are over your space quota`                | Ліміт 512 МБ: `npm run seed:clear` або менша кількість статей                                          |
| У PowerShell `curl` повертає дивні помилки               | Використовуйте `curl.exe` та екрануйте лапки в JSON як `\"`                                            |
